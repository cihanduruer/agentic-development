# Security

- GitHub Actions authenticates to Azure through OpenID Connect.
- The API uses its App Service system-assigned managed identity for Azure SQL, Azure AI Services, and Azure AI Search. The SQL runtime connection selects managed-identity authentication explicitly rather than a developer-oriented default credential chain. AI Services and Search local-key authentication is disabled.
- Azure SQL accepts Microsoft Entra authentication only. The runtime identity has a custom role limited to catalog reads, reservation reads/inserts, and operations-event reads/inserts/deletes for bounded retention; it is not a database owner and cannot migrate schemas.
- Prompt and worker-description inputs are untrusted and are sent to the Azure AI Content Safety Prompt Shields API before routing.
- Routing requires an Azure AI Search hit for the exact requested knowledge commit. Prompt attack detection, absent grounding, configuration failure, and service failure route to `human_review`.
- The dedicated manual Microsoft evaluation workflow is configured to invoke `azure.ai.evaluation.GroundednessEvaluator` and persist its JSON evidence. PR validation separately persists deterministic routing-gate test results. Until a successful workflow artifact exists for a revision, groundedness evaluation is configured but not live-verified for that revision.
- Operations events contain metadata only. Do not record prompts, source code, credentials, tokens, guest personal data, or tool output bodies.
- Correlation IDs are random identifiers, not user identifiers.
- CORS is allow-listed. Outside Development, operations ingestion and orchestration routing require an Entra v2 access token whose `aud` matches the configured API application client ID and whose `roles` claim contains `Operations.Ingest`. Token acquisition uses the API Application ID URI as a separate resource value. Missing authentication configuration prevents API startup.
- Development explicitly leaves operations writes and routing unauthenticated for local and integration-test use. Dashboard reads, SignalR, and public hotel-booking endpoints are not covered by the operations-writer policy.
- Event history is bounded by age, record count, and query limit. The deployed defaults are 30 days, 2,000 records, and 500 records per query.
- Dependencies, infrastructure, and application code are scanned in CI.

## SQL bootstrap

The SQL server's Microsoft Entra administrator must be the GitHub OIDC deployment service principal before the first pipeline run. This control-plane assignment is the unavoidable one-time manual prerequisite when the deploying identity cannot assign itself as SQL administrator. For the current development subscription it is already configured.

Each development deployment then performs the repeatable data-plane sequence:

1. Apply EF migrations as the Entra deployment principal.
2. Before any infrastructure mutation, classify the dedicated resource group's SQL state. A resource group with no SQL server is an initial deployment. An existing environment must contain exactly one server and must already name the GitHub deployment principal as SQL Entra administrator; missing, ambiguous, or inaccessible state fails closed before deployment. Existing SQL is excluded from the first Bicep phase so its current authentication mode remains live if migration or bootstrap fails.
3. Provision shared infrastructure without applying API configuration. If the API is new, create its system identity through `infra/api-identity.bicep`; an upgraded API is not modified during this phase. Initial-empty SQL is created Entra-only, while existing SQL is not changed.
4. Resolve the exact App Service system-assigned identity with `scripts/Resolve-AppServiceSqlIdentity.ps1`. Bind the authenticated subscription and expected tenant to the exact App Service resource ID, name, `Microsoft.Web/sites` type, `SystemAssigned` identity type, and absence of user-assigned identities. Read the scoped ARM `Microsoft.ManagedIdentity/identities/default` endpoint (API version `2024-11-30`) and require matching resource ID, resource type, principal object ID, and tenant ID plus a nonempty, distinct application/client ID. Project only safe metadata; never follow or print `clientSecretUrl`. Lookup failure or identity mismatch fails closed without Graph fallback or new directory permissions. Acquire an Azure SQL access token and run `tools/SqlManagedIdentityBootstrapper` with separate `--principal-object-id` and `--principal-client-id`. The object ID remains the verification/RBAC identity; only the client ID is converted from `uniqueidentifier` to `binary(16)` for `CREATE USER WITH SID, TYPE = E`. Both IDs participate in SQL identity-candidate uniqueness checks. The tool uses `Microsoft.Data.SqlClient` token authentication and parameterized inputs.
5. The `hotel_booking_runtime` role must be owned by `dbo`, have no permissions beyond the documented object grants, have no explicit database-principal permission targeting the role securable, and have the expected API principal as its sole direct member. Effective or inherited membership does not satisfy this direct-membership invariant. Create the role with explicit `AUTHORIZATION dbo`; an existing role with a null or different owner fails closed before any permission migration. Any explicit permission targeting the role, including delegated `ALTER`, `CONTROL`, or `TAKE OWNERSHIP`, fails closed before migration and in the final transaction postcondition because its grantee could otherwise change ownership or membership. The repository history establishes the seven-permission runtime-role contract, not a historical direct-grant operation against the API principal. As a narrowly bounded incident-recovery path, direct API object permissions may be converted only when they exactly equal that contract (`SELECT` on `dbo.Hotels` and `dbo.Rooms`; `SELECT` and `INSERT` on `dbo.Reservations`; `SELECT`, `INSERT`, and `DELETE` on `dbo.AgentEvents`). Ordinary database `CONNECT` is separate baseline access only for the exact catalog tuple `class=0`, `major_id=0`, `minor_id=0`, `permission_name=CONNECT`, `state=G`, with canonical `dbo` as grantor. Preserve that tuple when present; the bootstrap never explicitly grants or revokes `CONNECT`. Exclude only this tuple from the direct object-permission count, both exact-set comparisons, and the post-migration removal check. Transactionally revoke the exact seven direct object grants, prove that no nonbaseline direct permissions remain, and then grant membership only in `hotel_booking_runtime`. Baseline-only access also supports repeat bootstrap without object migration. Missing or additional object grants, any other database- or column-level permissions, `DENY`, grant option, a noncanonical `CONNECT` grantor or scope, an unexpected principal name/SID/type/authentication type, ownership, delegated role permissions, indirect membership, or unexpected role membership fails closed. Identity mismatch diagnostics include the expected and observed authentication type without relaxing this predicate.
6. Classify the API independently from SQL: an absent or identity-only API without a runtime SQL setting follows the initial path even when a prior failed attempt already created SQL. After SQL identity bootstrap, that path configures the API before deploying the artifact because no prior configured service exists. A configured upgrade deploys and proves the migration-disabled artifact while its existing SQL setting remains unchanged. A failing catalog blocks the normal path. A manual development run may continue only when the current setting is unambiguously one of the repository's passwordless managed-identity forms and the operator supplies the exact `RECOVER-STRANDED-MANAGED-IDENTITY` confirmation; legacy, mixed, unexpected-target, and unsupported settings remain blocked. The workflow then captures the prior setting, fails before mutation unless the temporary file is permission-restricted, refreshes the GitHub OIDC Azure login immediately before applying the managed-identity configuration, and proves a SQL-backed request. Any deployment or readiness failure obtains another fresh Azure login before restoring and proving the prior app setting. The temporary prior-setting and diagnostic files are deleted in an always step that fails unless absence can be proven. The pre-existing SQL authentication mode is observed separately so diagnostics never invent a legacy fallback for an already-Entra-only server. After managed-identity readiness succeeds, a separate SQL-only Bicep phase enforces Entra-only authentication and another SQL-backed request verifies the final state.
7. Automatic development deployments never delete the legacy credential. A separately confirmed manual development run may remove only the active legacy `sql-connection-string` after migration, managed-identity bootstrap, API deployment, and the operations persistence smoke all succeed. Production requires its own exact cleanup confirmation and waits for both API health and a successful SQL-backed catalog request. Cleanup never creates or broadens a role assignment. It uses the supported Key Vault data-plane delete operation with output suppressed and metadata-only absence verification. If the deployment identity lacks pre-provisioned metadata/delete access constrained to that secret, the workflow fails closed and an approved operator must delete that exact active secret and rerun verification.
8. Obtain a fresh GitHub OIDC Azure login in the always path, then remove the temporary GitHub runner firewall rule. Cleanup never relies on an assertion cached by an earlier deployment phase.

Failed development bootstrap runs may be investigated through the manual
`Diagnose development SQL permissions` workflow documented in
`docs/runbooks/development-sql-diagnostics.md`. The workflow is constrained to the
canonical tagged development SQL server, `hotelbooking` database, and development API
managed identity. It requires an exact typed confirmation, verifies the configured
GitHub OIDC identity is still SQL Entra administrator, creates one run-unique exact-IP
firewall rule, and executes only the bootstrapper's fixed parameterized diagnostic
`SELECT` with `ApplicationIntent=ReadOnly`. Its sanitized artifact records identity
candidates, direct permissions, all role-membership edges, ownership and
delegated-permission facts, observer metadata visibility, and `@@TRANCOUNT` for the
diagnostic session. A fresh OIDC login in an `always()` cleanup deletes only the exact
temporary rule and proves its absence. The diagnostic cannot target production,
deploy resources, change application configuration, or issue SQL permission or data
mutations.

No SQL login or SQL administrator password is used by the running API or stored in GitHub or application settings. After the explicitly approved cleanup, upgraded environments verify the absence of the active legacy Key Vault secret. Key Vault soft-delete and purge protection can retain a recoverable deleted version for the configured retention period; the deployment does not purge it or delete the vault because permanent purge is a separately approved irreversible operation.

### Opt-in correction of the historical object-ID SID

Ordinary bootstrap rejects an existing object-ID SID. A separately approved manual development or production deployment may supply `sql_object_id_sid_repair_confirmation=REPAIR-OBJECT-ID-SID`, passed to the tool as `--repair-object-id-sid REPAIR-OBJECT-ID-SID`. Automatic deployment and diagnostic mode cannot enable repair. This is independent of the stranded managed-identity app-setting recovery confirmation.

Repair accepts only the exact expected name, external-user type/authentication, and historical object-ID SID, with no other candidate matching either ID. Before dropping anything, require complete catalog visibility (`CONTROL` on the database), the existing `dbo`-owned runtime role with its exact seven `dbo` grants, sole API membership, only canonical `dbo` CONNECT on the API, no ownership, principal-target permissions, grantor dependencies, execution-context dependencies (SQL modules and Service Broker queue activation), or noncanonical user settings. Additional owned securable catalogs include types, assemblies, XML schemas, keys, certificates, full-text and Service Broker objects. Legacy seven-direct-object-grant recovery remains separate and is not accepted during SID repair.

Within the existing rollback-protected transaction, remove the exact membership, drop and recreate the same user with the verified client-ID SID, and restore the exact runtime-role membership. SQL user creation supplies CONNECT; do not issue an extra CONNECT grant or revoke. Before commit, verify the final SID/type/authentication, canonical CONNECT, and exact runtime role contract. Unexpected state or failure rolls the transaction back; no arbitrary SID adoption, permission widening, or ownership transfer is allowed. Already-correct identities remain idempotent with or without the confirmation.
