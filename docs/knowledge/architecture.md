# Architecture

## Application

The MVP is a modular monolith:

- Blazor WebAssembly serves the booking journey and operations dashboard.
- ASP.NET Core exposes hotel, availability, reservation, and agent-event APIs.
- Domain contains rules and records.
- Application contains use-case and telemetry contracts.
- Infrastructure contains replaceable implementations.

Entity Framework Core stores the catalog, reservations (including an optional vehicle-preference category), and AI operations events in Azure SQL. Room amenity data is part of the room catalog and is returned by the existing hotel and availability DTOs; the guest UI derives filter choices from the selected hotel's catalog and refines the availability response client-side with match-all semantics. No amenity filter leaves the API availability set unchanged. Vehicle preferences are accepted only during reservation creation; reservation updates are not supported, and `PUT` or `PATCH` requests to `/api/reservations/{reservationId:guid}` return HTTP 409 Conflict without modifying the reservation. The running API authenticates explicitly with its App Service system-assigned managed identity through Microsoft Entra ID and receives only the custom `hotel_booking_runtime` database role. The GitHub OIDC deployment principal, configured as the SQL Entra administrator, applies migrations and idempotently creates the contained API user; the runtime does not migrate schemas or use SQL administrator credentials. Reservation creation uses a serializable transaction and an indexed overlap query to preserve atomic overlap protection. Operations-event writes prune records older than the configured age and records beyond the configured capacity; reads clamp caller-supplied limits before issuing an ordered database query. Local and integration execution uses the EF in-memory provider with the same application services.

Static Web Apps rewrites client-side routes to the Blazor `index.html`, so direct navigation to SPA routes loads the application. The public navigation is booking-only. Delivery overview, architecture, and operations routes are `/admin`, `/admin/architecture`, and `/admin/operations`; `/architecture` and `/operations` redirect to the corresponding admin route. These pages are not protected by sign-in or authorization in the current web app. Deployment writes the environment-specific HTTPS API endpoint to `appsettings.json` and removes publish-time Brotli and gzip variants of that runtime configuration; a browser must never receive a precompressed variant containing the local development endpoint.

The `/admin` delivery overview calls the API's `GET /api/delivery/status` read path; the browser never calls GitHub or Azure Boards directly. The API reads public GitHub repository issues, open/merged pull requests, and allowlisted workflow runs, then optionally projects the selected delivery's Azure Boards state, tags, changed date, canonical URL, and typed safe links. The implementation is in `src/Infrastructure/DeliveryStatusService.cs`, the route is in `src/Api/Program.cs`, and the accessible UI is in `src/Web/Pages/Admin.razor`. It only reports evidence returned by those sources; absent stage evidence is `Not started` (except the Derived intake and cloud-agent stages described in `agentic-delivery.md`), failures do not fabricate progress, and cached data is marked stale on upstream failure. In particular, a `Copilot cloud agent` workflow run is the direct evidence for the cloud-agent stage; the repository's `Copilot setup steps` workflow is never treated as evidence that the agent completed work. GitHub reads use two Actions endpoint requests and conditional ETags where available; the 45-second API cache (5 minutes without a GitHub token) and stale-on-rate-limit fallback remain in place. The visible page polls every 20 seconds while the tab is visible.

Azure Boards is allowlisted to `ai-enabled-ado-org/sample-project` and only queried by GET for a positive integer AB# ID present in recent GitHub deliveries. Its projection excludes raw work-item payloads, descriptions, comments, assignees, attachments, and arbitrary query results. Managed identity is preferred; PAT mode is supported only through protected application configuration. The App Service identity still requires manual Azure DevOps organization service-principal provisioning; until that is completed and verified, the connection is explicitly unverified or not connected. See `docs/runbooks/boards-status-connector.md`. GitHub uses public read-only metadata without a token; an optional read-only token is supplied only through protected app configuration. Neither connector claims live cloud verification from source or fake-HTTP tests.

The `/admin/architecture` page is a static, accessible map of the Hotel services declared in `infra/modules/platform.bicep` and the Boards/GitHub path described by `.github/workflows/` and `docs/knowledge/agentic-delivery.md`. It now labels the GitHub status read path: browser -> API `GET /api/delivery/status` -> GitHub public API and (when configured) Azure Boards. Every numbered connector has a visible label naming its configured call or delivery action. Moving dots are decorative, never live traffic; the numbered prose remains sufficient when reduced motion is requested. SKU labels are declarations from Bicep, not live resource discovery. Azure AI Content Safety Prompt Shields, exact-revision Azure AI Search, and optional Azure OpenAI through Microsoft Agent Framework remain separate stages in the existing runtime routing contract.

The Hotel service map covers Azure Static Web Apps with Blazor WebAssembly, the App Service ASP.NET Core API and its hosted SignalR hub, Azure SQL, Azure AI Search, Azure AI Content Safety, Azure OpenAI through Microsoft Agent Framework, and Application Insights with Log Analytics. Its delivery path is Azure Boards into GitHub issues/cloud-agent work, pull-request validation/review/QA, merge, development deployment, lifecycle synchronization, release proposal, and a human-approved manual production promotion. The relevant delivery sources are `.github/workflows/agentic-intake.yml`, `pr-validation.yml`, `hotel-code-review.yml`, `qa-evidence.yml`, `deploy-development.yml`, `sync-development-lifecycle.yml`, `release-proposal.yml`, and `deploy-production.yml`.

## Operations

The API exposes a typed event-ingestion endpoint and broadcasts accepted events through SignalR after persistence succeeds. The dashboard reloads bounded recent history and receives live events. Dashboard reads and the SignalR hub remain public, while event ingestion and routing require the `Operations.Ingest` Entra application role outside Development. Production telemetry is correlated through Application Insights and retained in Log Analytics; sensitive prompt bodies and source code are not dashboard fields.

## Agent workflow

GitHub Copilot agents perform repository work. Deterministic C# policy owns safety, evidence, and approval gates. For ambiguous safe routes, Microsoft Agent Framework obtains strict typed output from an Azure OpenAI deployment and validates the suggestion against the live worker menu and confidence threshold. Azure AI Search supplies revisioned knowledge, Azure AI Content Safety supplies Prompt Shields, and the dedicated Microsoft Foundry evaluation workflow is configured to score groundedness when manually dispatched. These signals never grant authorization. Repository tests prove the deterministic fail-closed behavior; deployment and live-cloud workflow evidence are separate release artifacts and must not be inferred from local validation.

`tools/KnowledgeIndexer` reads only canonical Markdown under `docs/knowledge`, requires `owner` and `last_reviewed` front matter, chunks on section boundaries, and uses deterministic revision/path/content hashes as Azure AI Search keys. Re-running the same commit uses `mergeOrUpload` and does not duplicate chunks; prior revisions remain queryable.

`tools/KnowledgeMcp` is a separate ASP.NET Core remote MCP service, not an API or web application endpoint. Its only tool, `search_knowledge`, reads the fixed `knowledge` index, filters by one full requested commit SHA and canonical `docs/knowledge/` paths, and returns bounded passages with exact-revision GitHub source links and document metadata. It rejects wildcard and operator-only queries, requires every focused subject keyword to match the passage content using Azure Search `SearchMode.All`, sends only literal alphanumeric query terms to Search, and validates all terms against the final bounded passage before returning evidence. Its HTTP transport is explicitly stateless, so requests do not depend on session affinity or an `Mcp-Session-Id`; clients send the negotiated protocol version on requests after initialization. The service uses only its system-assigned managed identity for Azure AI Search. The source implementation is not evidence that the service is deployed or connected to a Copilot client; the POC runbook records the remaining hosted setup and demonstration gates.

The manual `deploy-knowledge-mcp.yml` workflow builds only an exact reviewed SHA dispatched from `main`. Its dedicated resource-group Bicep template creates an isolated Linux F1 Free app plan and MCP app, and grants that app's system identity Search Index Data Reader only on the existing Search service. F1 sleep/cold-start and CPU quotas are accepted for this disposable POC; the paid Hotel API plan is never reused and there is no paid-tier fallback. A bounded post-deployment MCP smoke records sanitized protocol and exact-revision Search evidence as a durable workflow artifact; that is separate from Copilot client demonstrations.

Before any automated worker route is selected, the API invokes Azure AI Content Safety Prompt Shields over routing metadata and the live worker descriptions, then queries Azure AI Search for evidence matching the exact requested commit revision. Detection, missing or malformed evaluation evidence, configuration errors, and service errors all deterministically select `human_review`. Microsoft Agent Framework is reached only after these gates pass. The API authenticates to AI Services and Search with its Entra managed identity; local keys remain disabled. Model input is restricted to routing metadata and worker IDs. All decisions are emitted through the existing operations event stream and correlated in Application Insights.
